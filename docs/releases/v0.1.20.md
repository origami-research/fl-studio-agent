# fl-studio-agent 0.1.20

The server now refuses to drive a controller script it does not match, and an error inside `run` shows how to fix it.

## Install

```bash
claude mcp add --scope user fl-studio -- uvx --python 3.12 fl-studio-agent
```

Cursor and VS Code: use the install buttons in the [README](https://github.com/origami-research/fl-studio-agent#quick-start).
Claude Desktop: download `fl-studio-agent.mcpb` below and open it.
Then set up FL Studio once, with FL closed (on Windows, in a terminal opened as administrator on your own account):

```bash
uvx --python 3.12 --from fl-studio-agent fl-mcp-install
```

Then open `FLMCP Agent.flp` in FL Studio before you ask for music; it carries the Bridge.

## Updating

If you upgrade with pip (or any way other than a fresh install), rerun `fl-mcp-install` once, with FL closed:

```bash
uvx --python 3.12 --from fl-studio-agent@latest fl-mcp-install
```

From this release the server sends nothing to a controller script that is not the one it installs.
Until you rerun the installer, every live call is refused with an error that names the installed and the needed controller version.
The controller script is the same as in 0.1.19, so if you already reran the installer for 0.1.19 you are set.
`fl-mcp-doctor` reports a stale controller.

## Changes

- **A stale controller is refused instead of driven** (#363).
  Before, the server only logged a warning and kept talking to an old controller script.
  A controller older than 0.2.9 could freeze FL, and an upgrade without rerunning `fl-mcp-install` kept one in place.
- **An error raised inside `run` names its fix** (#365).
  The cell's traceback now ends with the error's message and then a `Fix:` line, which before reached the model only when a tool call failed outside `run`.
- **`fl.separate` docs** (#364).
  The docstring says the output name must be a plain file name ending in `.wav`.
  Its timing now reads about 20 s per minute of audio, plus about 40 s for the first call while the model loads, measured on a 2-vCPU Windows machine with FL running.
  The 0.1.19 notes said about 10 s per minute, a Linux figure.

## Known issues

- `fl.separate` has been checked on made-up test mixes only, not on recorded music.
- `fl.scene()` takes about 4 s, more with many patterns.
- The project's notes follow a channel's name, so a channel FL renames (a loaded sample or preset) loses its line.
- The sound model and index are still unpublished, so `fl.sounds` ranks by name only and `like=` is refused.
- On Intel macOS, and on Python 3.15 and later, onnxruntime has no wheel, so `fl.separate` is unavailable and `fl.sounds` matches by name only there.
- FL keeps automation about 0.1 s later than asked for (measured on one machine); the `sidechain` guide starts each dip that much early.
- On Windows, a program that opens the null device `NUL` itself is still refused inside `run`; use `subprocess.DEVNULL` or `os.devnull`.
- A render plays in real time, so `stems=` takes one play per stem.
- The MCP server's description (`...; confined=true`) is meant for the host, but some MCP clients may show it.
