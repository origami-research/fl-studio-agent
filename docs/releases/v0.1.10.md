# fl-studio-agent 0.1.10

FL no longer stops answering in the middle of a session: automating, rendering and meter checks could freeze the controller, most often during `fl.automate`.
The agent project's Cowbell and Sampler channels also play into their own mixer tracks.

## Install

```bash
claude mcp add --scope user fl-studio -- uvx --python 3.12 fl-studio-agent
```

Cursor and VS Code: use the install buttons in the [README](https://github.com/origami-research/fl-studio-agent#quick-start).
Claude Desktop: download `fl-studio-agent.mcpb` below and open it.
Then set up FL Studio once, with FL closed (on Windows, in a terminal opened as administrator on your own account):

```bash
uvx --python 3.12 --from fl-studio-agent fl-mcp-install
```

Then open `FLMCP Agent.flp` in FL Studio before you ask for music; it carries the Bridge.

## Updating from 0.1.9 or earlier: rerun fl-mcp-install

The FL controller script is now 0.2.9, and the fix below lives in it.
After updating, close FL and run `fl-mcp-install` again (the command above), then reopen FL.
Until you do, the server reports the installed controller as stale and the old controller can still freeze.

## Fixes

- **FL stopped answering for good** (#328, #330).
  FL runs the controller's MIDI callback on its MIDI input thread, and the controller sent its answers from there; that send waited for FL's main thread while the main thread waited on the MIDI thread.
  FL's window kept responding, but the controller never answered again.
  It struck `fl.automate` (the pumping recipe froze FL in the first take of a test), renders and meter checks, more often the larger the request.
  The controller now runs requests and sends answers from FL's main thread.
  A request FL could not run in time (FL does not run them while it shows a dialog) is dropped rather than run late, so a change reported as failed does not land afterwards.
  On a test machine, replays of the frozen takes froze FL in 3 of 3 before; after, 96 of 96 automation takes and 44 of 44 renders ran through, on 4-CPU and 2-CPU machines.
  FL answers on its main thread now, which a busy machine can hold for seconds, so each request waits up to 8 s.
- **Cowbell and Sampler 1 to 3 played into the Choir's mixer track** (#329).
  `fl.channels` said so (mixer track 19), and it was right; the template now routes them to their own tracks (10, 20 to 22), as the mixer's names and the project notes say.
  Projects made from an earlier template keep the old routing; `fl.route` moves a channel.
- The agent project's notes no longer say the kick ducks Synth Bass.

## Known issues

- FL keeps automation about 0.1 s later than asked for (measured on one machine); the pumping recipe starts each dip that much early.
- Each request waits for FL's next idle moment (about 0.1 s on a busy 2-CPU machine), so an 8-bar automation takes about 37 s instead of 33 s, and no request is answered while FL shows a dialog.
- On Windows, a program that opens the null device `NUL` itself is still refused inside `run`; use `subprocess.DEVNULL` or `os.devnull`.
- A render plays in real time, so `stems=` takes one play per stem.
